# Pi 0.84.3 native PowerShell: security and capability comparison

Research date: 2026-08-24
Release examined: Pi `v0.84.3`, commit [`4e58f324fae8ebfa98a3d45181fb248072a2afac`](https://github.com/earendil-works/pi/commit/4e58f324fae8ebfa98a3d45181fb248072a2afac)

## Bottom line

Pi 0.84.3 makes a third-party extension unnecessary for **ordinary foreground PowerShell commands**. It does **not** make `pi-pwsh-notify-secure` wholly moot: the native tool has no persistent working directory, managed background jobs, job wait/output/list/kill interface, or automatic ready/finished steering notifications. It also does not retain the fork's stricter executable-resolution and execution-policy posture.

For a user who needs only foreground PowerShell and accepts Pi's local-user trust boundary, the built-in tool is the simpler choice. For this audit's stricter threat model, or for no-polling background jobs, the hardened fork still provides material functionality and hardening.

Pi labels the feature **optional**. The standard built-in set remains `read`, `bash`, `edit`, and `write`; Windows users must select `powershell` in `defaultTools`. The editor's `!` and `!!` commands still use Bash. [Release notes](https://pi.dev/news/releases/0.84.3) · [Windows documentation](https://pi.dev/docs/latest/windows) · [default tool selection at the release commit](https://github.com/earendil-works/pi/blob/4e58f324fae8ebfa98a3d45181fb248072a2afac/packages/coding-agent/src/core/agent-session.ts#L2721-L2729)

## Security assessment

The native tool is first-party and dramatically reduces third-party code surface for the foreground-only case, but Pi 0.84.3 does not implement the two hardening points that motivated the private fork:

1. **Executable discovery and cleanup helpers are not pinned to trusted absolute paths.** `findExecutableOnPath()` launches the bare name `where` and accepts its first existing result; `killProcessTree()` launches the bare name `taskkill`. The selected PowerShell path is usually absolute after discovery, but the discovery and cleanup chain still depends on ambient Windows executable resolution. This is weaker than the fork's explicit absolute-candidate invariant. [resolver source](https://github.com/earendil-works/pi/blob/4e58f324fae8ebfa98a3d45181fb248072a2afac/packages/coding-agent/src/utils/shell.ts#L24-L51) · [cleanup source](https://github.com/earendil-works/pi/blob/4e58f324fae8ebfa98a3d45181fb248072a2afac/packages/coding-agent/src/utils/shell.ts#L216-L228)
2. **Every native call requests process-local `ExecutionPolicy Bypass`.** Pi documents this explicitly and notes that administrator-enforced policies can still win. The fork intentionally removed the flag. [official Windows docs](https://pi.dev/docs/latest/windows) · [release source](https://github.com/earendil-works/pi/blob/4e58f324fae8ebfa98a3d45181fb248072a2afac/packages/coding-agent/src/utils/shell.ts#L122-L136)

Pi's own published security boundary treats the local user account, environment, workspace, shell startup files, and Pi configuration as one trust boundary and states that Pi is not a sandbox. Under that documented model, the native implementation may be acceptable. It does not, however, satisfy the stricter untrusted-workspace/executable-resolution standard used in this package audit. [Pi security policy](https://github.com/earendil-works/pi/blob/4e58f324fae8ebfa98a3d45181fb248072a2afac/SECURITY.md)

## Practical recommendation

- Use native `powershell` and remove this extension if foreground commands are the whole requirement and the points above fit the accepted trust model.
- Keep `pi-pwsh-notify-secure` for persistent `cd`, managed long-running jobs, blocking wait without polling, and metadata-only ready/finished notifications.
- Do not treat 0.84.3 as a security superset of the hardened fork. A cleaner long-term endpoint would be upstream absolute helper/shell resolution and an opt-out or removal of forced `ExecutionPolicy Bypass`; after that, the extension could potentially shrink to only the background-job/notification layer.
